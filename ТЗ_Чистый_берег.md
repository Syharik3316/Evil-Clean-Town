# ТЗ: «Чистый берег» — платформа популяризации экологического мониторинга ДЗЗ

## 1. Разбор кейса

**Кто в проекте:** Фонд защитников природы (заказчик/смысл), «СР Дата» (частная космическая ИТ-компания — источник спутниковых данных ДЗЗ), Яндекс.Облако (инфраструктура/облако).

**Что реально просят:** *«серия мероприятий ИЛИ приложение для популяризации образовательного проекта»* — то есть акцент на **вовлечение и просвещение**, а не на создание профессионального инструмента геоанализа. Слово «популяризация» — ключевой критерий: жюри интересует охват, понятность и вовлечённость аудитории, а не точность спутниковой аналитики.

**Вывод:** делаем гибрид — не просто медиа-контент и не сухой ГИС-инструмент, а продукт, который:
- объясняет сложные данные ДЗЗ простым языком,
- превращает их в историю про конкретный берег,
- вовлекает людей физически (уборки) и онлайн (обучение, данные, геймификация).

---

## 2. Концепция продукта

**Идея:** веб/мобильное приложение (+ при желании оффлайн-компонент), которое берёт спутниковые снимки конкретных участков побережья, показывает их «до/после» в понятном виде, обучает пользователя базовым принципам ДЗЗ через короткие интерактивные уроки и вовлекает в реальные и виртуальные активности (уборки, квесты, citizen science — сбор данных руками пользователей).

**Elevator pitch (черновик):** «Чистый берег» — платформа, которая показывает твоему городу его настоящий берег глазами спутника, учит понимать эти данные за 5 минут и помогает организовать/найти уборку рядом с тобой.

## 3. Целевая аудитория

| Сегмент | Потребность |
|---|---|
| Школьники/студенты | Понятное экопросвещение, геймификация, школьные задания |
| Волонтёры существующих эко-акций | Календарь мероприятий, учёт вклада, сообщество |
| Учителя/эко-клубы/вузы | Готовые учебные модули, инструмент для урока |
| Широкая аудитория соцсетей | Вирусный контент, простые визуализации, шеринг результата |

---

## 4. MVP-функционал (приоритет для хакатона)

1. **Карта побережья со слоями ДЗЗ** — переключение «до/после» или временной ползунок, индекс замусоренности/растительности/мутности воды (NDVI и аналоги). Если нет доступа к реальному API — можно на демо использовать заранее подготовленные пары снимков.
2. **Короткие обучающие модули** (3–5 карточек/лонгридов): что такое ДЗЗ, как читать спутниковый снимок, почему пластик опасен для берега, как работает мониторинг.
3. **Геймификация**: баллы, ачивки, рейтинг пользователей/школ/городов за прохождение уроков и участие в активностях.
4. **Календарь мероприятий + регистрация** — уборки, вебинары, эко-квесты, с гео-чекином для подтверждения участия.
5. **Citizen science**: загрузка фото мусора с берега (простая модерация вручную на MVP, ML-классификация — если хватит времени).
6. **Профиль пользователя/команды/школы** с прогрессом и историей участия.
7. **Соц-шеринг** результата («мой вклад», «мой уровень эко-грамотности»).

## 5. Доп. функционал (если останется время)

- AR-режим «наведи камеру — увидь состояние берега по спутниковым данным»
- Чат-бот/ассистент, объясняющий данные простым языком (можно на базе LLM)
- Push-уведомления о ближайших уборках по геолокации
- Дашборд для фонда/организаторов — агрегированная статистика по регионам, вовлечённости

## 6. Роли пользователей

- **Гость / волонтёр** — проходит обучение, участвует в мероприятиях, загружает данные
- **Организатор** (школа, эко-клуб, фонд-партнёр) — создаёт мероприятия, модерирует

## 7. Технологический стек

### Веб (основа)
- Frontend: React (Vite) или Next.js + Tailwind
- Карта: Leaflet или Mapbox GL JS (поддерживают спутниковые тайлы и кастомные слои)
- Backend: Node.js (Express/Fastify) или Python (FastAPI)
- БД: PostgreSQL (можно поднять быстро через Supabase для скорости на хакатоне)
- Хостинг: **Яндекс.Облако** — стоит явно использовать инфраструктуру спонсора, это обычно бонус у жюри

### Перенос на мобильные — сравнение вариантов

| Вариант | Плюсы | Минусы | Когда выбрать |
|---|---|---|---|
| **PWA** | Мгновенно устанавливается из браузера по ссылке, не нужен стор, минимум доп. кода | Ограниченный доступ к части нативных API, чуть менее «нативное» ощущение | Лучший вариант для демо на хакатоне — жюри просто открывает ссылку с телефона |
| **Capacitor** (то, что вы и описали, аналог механизма Discord-обёртки, но для мобилок) | Тот же веб-код + нативная оболочка, доступ к камере/геолокации/пушам через плагины, можно собрать реальный .apk | Дольше настраивать сборку и подписание, для iOS нужен Mac/Xcode | Если хотите показать «настоящее» приложение и есть время на сборку |
| React Native / Flutter (с нуля) | Полностью нативный UX | Отдельная кодовая база — не то, что вы описали, и слишком долго для хакатона | Не рекомендую в сроки хакатона |

**Рекомендация:** делайте адаптивный (mobile-first) веб-сайт как единственную кодовую базу. На демо показывайте его как PWA (устанавливается за 10 секунд). Если останется время в конце — соберите Capacitor-обёртку как «вишенку на торте» для питча («у нас уже готов и нативный билд»).

## 8. Источники данных ДЗЗ

- **Sentinel Hub / Copernicus Open Access Hub** — открытые спутниковые снимки Sentinel-2, есть бесплатный тир, хорошо подходит для демо NDVI и изменений береговой линии
- Уточнить у организаторов, даёт ли **«СР Дата»** участникам доступ к своим данным/API — раз это их профиль, велика вероятность, что такой доступ будет частью хакатон-пакета
- Если интеграция окажется сложной за отведённое время — заранее подготовьте 2–3 пары снимков «до/после» одного и того же участка берега как статичный демо-датасет. Для хакатона это абсолютно нормальная практика.

## 9. Поэтапный план (ориентир на хакатон ~48 часов, скорректируйте под свои сроки)

**Старт**
- Финализировать концепцию, распределить роли в команде (фронт / бэк+данные / дизайн / питч)
- Быстрые wireframes ключевых экранов (карта, урок, лента мероприятий, профиль)

**День 1, первая половина**
- Настройка репозитория, деплой заглушки
- Интеграция карты + подготовка демо-датасета снимков
- Каркас навигации и дизайн-система (цвета, шрифты, компоненты)

**День 1, вторая половина**
- Логика обучающих модулей + геймификации (баллы, ачивки)
- Календарь мероприятий + регистрация

**День 2, первая половина**
- Citizen science (загрузка фото + модерация)
- Адаптация под мобильный экран, тест как PWA
- (опционально) Capacitor-сборка

**День 2, вторая половина**
- Полировка UI, исправление багов
- Подготовка сценария демо и презентации
- Прогон питча с таймингом

## 10. На что вероятно будет смотреть жюри

- Соответствие сути кейса — именно **популяризация и вовлечение**, а не техническая сложность
- Работающее живое демо важнее идеального, но нефункционального дизайна
- Использование инфраструктуры спонсора (Яндекс.Облако) — явный плюс
- Наличие конкретного кейса/истории (реальный или правдоподобный участок берега) вместо абстрактной демонстрации
- Понятность для «не-эксперта» — попробуйте показать продукт человеку не из темы ДЗЗ и проверить, понятно ли ему

---

## 11. Риски и как упростить, если не хватает времени

- Если интеграция реального ДЗЗ API не успевает — используйте заранее подготовленные снимки, это не снизит оценку за «популяризацию»
- ML-классификация мусора — красивая фича, но не критичная; можно оставить ручную модерацию
- Если не успеваете с Capacitor-сборкой — сдавайте как PWA, это не будет минусом
- Сокращайте функционал в порядке: доп. фичи (п.5) → мобильная обёртка → MVP-фичи оставляйте как ядро
